# SSE event contract — chat & inbox

**Status:** v1 · **Owner:** backend · **Consumers:** chat page, inbox live updates

Two kinds of streams share this contract:

1. **Chat turn stream** (built): `POST /public/chat/{slug}/messages` streams one assistant turn
   (`delta`, `tool_status`, `system`, `error`, `done`). It ends with `done`.
2. **Live conversation streams** (built): a visitor stream for one thread and an owner inbox
   stream for all of a merchant's threads. They carry persisted `message` and
   `conversation_update` events.

Every frame is `data: <json>\n\n`. Comment frames (`: connected`, `: keepalive`) may appear and
must be ignored. Live conversation streams do not end on their own; reconnect when the connection
drops. A chat turn stream ends with `done`.

## Endpoints

| Endpoint | Auth | Scope |
|---|---|---|
| `POST /public/chat/{slug}/messages` | `Authorization: Bearer <visitor_token>` | One agent turn for a thread |
| `GET /public/conversations/{conversation_id}/stream` | `Authorization: Bearer <visitor_token>` | That one thread |
| `GET /conversations/stream` | `Authorization: Bearer <dashboard JWT>` | Every thread owned by the merchant |

The chat-turn body is:

```json
{"conversation_id": "8b0e…", "content": "Do you deliver on Sundays?"}
```

On success it returns `200 text/event-stream`; no `Accept` negotiation is required. Errors before
the stream starts use normal JSON error responses. The customer message is persisted before the
agent runs, so it remains in history if the model fails.

**Use `fetch()` with a streaming response body, not native `EventSource`.** `EventSource` cannot
send an `Authorization` header, and tokens must never go in query strings (they leak into logs).
Read the body with `response.body.getReader()` and split frames on `\n\n`.

```js
const response = await fetch(url, {
  headers: { Authorization: `Bearer ${token}`, Accept: "text/event-stream" },
});
const reader = response.body.getReader();
// decode chunks, buffer, split on "\n\n", JSON.parse each data line
```

## Live event types (built)

| `type` | Payload | When |
|---|---|---|
| `message` | `{"conversation_id": "uuid", "message": <message object>}` | A message was persisted (visitor stream receives staff/system messages; inbox receives all messages) |
| `conversation_update` | `{"conversation": <conversation summary>}` | Status changed (`handoff_requested`, `human_active`, `ai`, `closed`) |

Unknown `type` values must be ignored (forward compatibility).

### Message object

```json
{
  "id": "e2c1…",
  "role": "staff",
  "content": "Hi Ada — checking with the courier now.",
  "meta": {"kind": "handoff"},
  "created_at": "2026-10-30T13:01:00Z"
}
```

`role` is one of `customer`, `agent`, `staff`, `system`, `tool`. Render `system` messages as
distinct non-AI bubbles. `meta.kind` is `chat` for ordinary agent replies and `handoff` or
`payment` for system messages today.

### Conversation summary

```json
{
  "id": "8b0e…",
  "status": "human_active",
  "channel": "web",
  "customer_name": "Ada",
  "customer_contact": "ada@example.com",
  "handoff_reason": "I need help with a delivery",
  "last_message_at": "2026-10-30T13:01:00Z",
  "started_at": "2026-10-30T13:00:00Z"
}
```

### Frames

```
data: {"type":"message","conversation_id":"8b0e…","message":{"id":"e2c1…","role":"system","content":"The owner joined the chat.","meta":{"kind":"handoff"},"created_at":"2026-10-30T13:01:00Z"}}

data: {"type":"conversation_update","conversation":{"id":"8b0e…","status":"human_active","channel":"web","customer_name":"Ada","customer_contact":"ada@example.com","handoff_reason":"I need help with a delivery","last_message_at":"2026-10-30T13:01:00Z","started_at":"2026-10-30T13:00:00Z"}}
```

Inbox clients should treat `message` events as “refresh/patch this thread” signals — the full
message list is always available from `GET /conversations/{id}/messages`.

## Chat turn event types (built in the agent core)

| `type` | Payload | When |
|---|---|---|
| `delta` | `{"text": "..."}` | Agent token stream — append to the current assistant bubble |
| `tool_status` | `{"tool": "search_catalogue", "state": "started"\|"done", "label": "checking the catalogue"}` | A server-side tool call starts/finishes — show a status chip |
| `order_update` | `{<order draft object>}` | Reserved for the ordering-tools slice; not emitted yet |
| `system` | `{"kind": "receipt"\|"handoff"\|"payment"\|"reminder", "text": "..."}` | Non-model messages generated by the system. `handoff` is emitted now; the other kinds are reserved |
| `error` | `{"code": "rate_limited"\|"grounding_fail"\|"internal", "message": "..."}` | Terminal error for this turn. `internal` is emitted now; the other codes are reserved |
| `done` | `{}` | Terminal — this turn is complete |

Current tool labels are `checking the store information`, `checking the catalogue`, and
`connecting you to the seller`.

### Chat turn frame examples

```
data: {"type":"delta","text":"Sure — the scarf is "}

data: {"type":"tool_status","tool":"search_catalogue","state":"started","label":"checking the catalogue"}

data: {"type":"tool_status","tool":"search_catalogue","state":"done","label":"checking the catalogue"}

data: {"type":"system","kind":"handoff","text":"A person from Ada's Closet will reply here."}

data: {"type":"error","code":"internal","message":"The assistant hit a problem. Please try again."}

data: {"type":"done"}
```

## Client rules

1. Append `delta.text` to the in-progress assistant message; create the bubble on first delta.
2. `tool_status` chips are transient UI; clear them when the turn ends.
3. `order_update` replaces the entire order card (no client-side merging).
4. A `system` message is rendered as a distinct, non-AI bubble (receipt/handoff/payment/reminder).
5. On `error`, stop rendering deltas, show the message, and allow retry unless `code=rate_limited`.
6. On `message`, append the message if it is not already in the list (deduplicate by `message.id`).
7. On `conversation_update`, replace the thread's status/customer fields.
8. Ignore unknown `type` values.

## Order object (used by `order_update`)

```json
{
  "id": "uuid",
  "status": "draft",
  "currency": "USD",
  "items": [
    {"product_id": "uuid", "variant_id": null, "name": "Silk scarf", "variant": null, "qty": 1, "unit_price": "25.00"}
  ],
  "subtotal": "25.00",
  "delivery_fee": null,
  "total": null,
  "delivery_details": null,
  "approval_link": null
}
```

Money values are decimal **strings** (never floats). `total` is null until the order is confirmed;
the server computes it — the client never does.
